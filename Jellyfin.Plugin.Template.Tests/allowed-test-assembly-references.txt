# Every assembly the test project is allowed to reference, one simple name per
# line. Blank lines and lines starting with # are ignored.
#
# SuiteAssemblyReferencesTests reads this file and refuses in both directions: a
# reference the list does not name, and a name the list holds that the test
# assembly no longer references. The plugin's own list beside this one is the
# same shape for a different reason, and the argument for reading the built
# assembly rather than the project file is written there.
#
# What this exists for is the third condition on #44: the default run needs no
# container runtime, and a test that needs a server belongs in a named group
# outside the suite rather than inside it. Both of the shapes that condition is
# about arrive here as a reference. A container client is a package the tests
# drive, and a process launch is System.Diagnostics.Process, which the compiler
# writes into this assembly the moment a test names it. Neither is on this list,
# so neither arrives quietly.
#
# These are simple assembly names rather than package names, because that is
# what the compiler writes into the assembly and therefore what can be read back
# out of it. A package restored and never used emits no reference and is
# invisible here; it will fail this list on the day a test first uses one.

# The plugin, which is what the suite is about.
Jellyfin.Plugin.Template

# The server's own assemblies. The tests reference them with their runtime
# assets kept, because a test host has no server to supply them, which the test
# project file says beside the two package references.
#
# Jellyfin.Data is here for one type and it is #89's, the same one the plugin's
# own list names: the item kind a library query asks about, which the adapter's
# tests read back off the query it built.
Jellyfin.Data
MediaBrowser.Common
MediaBrowser.Controller
MediaBrowser.Model

# The one ASP.NET Core type in this suite. The server's host interface names
# HttpRequest in one of its methods, so the fake that implements the interface
# names it too. It is the framework the server itself runs on rather than
# something the tests brought in.
Microsoft.AspNetCore.Http.Abstractions

# Dependency injection. The abstractions are what the plugin's registrator is
# handed; the implementation is the container the tests build to see what came
# out of it, which is ServiceProvider and the extension that constructs one.
Microsoft.Extensions.DependencyInjection
Microsoft.Extensions.DependencyInjection.Abstractions

# The client factory, and it is here for #45's second condition rather than for
# anything the suite fetches. The injection point that condition asks for is one
# named client this plugin registers, so a test that puts a substitute in front
# of it configures a client, which is this assembly. It opens nothing: what it
# configures is a handler that answers what the test set up and refuses every
# other address, and the default client gets a second one with nothing set up on
# it at all, so a call made through the wrong client is refused here instead of
# leaving the runner.
Microsoft.Extensions.Http

# The logging abstractions, for the loggers a test passes in and reads back.
Microsoft.Extensions.Logging.Abstractions

# One attribute, on generated code rather than in anything anybody wrote:
# TestSDKAutoGeneratedCode, which Microsoft.NET.Test.Sdk puts on the entry point
# it generates for the test host.
Microsoft.VisualStudio.TestPlatform.ObjectModel

# The test framework.
xunit.abstractions
xunit.assert
xunit.core

# Runtime facades. Not dependencies in any useful sense: they are how the
# compiler spells a type that lives in the runtime the test host already runs
# on. System.ComponentModel is here for one type, IServiceProvider, which is
# forwarded there and is named by the fake host.
System.Collections
System.ComponentModel
System.Linq
System.Memory
System.Runtime

# Also from that runtime, and named separately because these are parts of it the
# suite reaches for rather than spellings of a type.
#
# System.Net.Http and System.Net.Security are the failure the transport hands
# back where a certificate is refused, which is an HttpRequestException wrapping
# an AuthenticationException; System.Net.Primitives is IPAddress, named by two
# methods of the fake host. None of the three opens anything: no test in this
# suite makes a connection, which is #46.
#
# System.Text.Json is what a source response is read with, System.Xml.ReaderWriter
# and System.Xml.XmlSerializer are what a configuration document is read and
# written with, and System.Text.RegularExpressions is the generated matchers the
# configuration page reader uses.
#
# System.Threading and System.Threading.Thread are the two threads and the gate
# between them in the store's concurrent-write test. Threads rather than a wait:
# nothing here sleeps, which is what no-sleep-in-a-test refuses.
System.Net.Http
System.Net.Primitives
System.Net.Security
System.Text.Json
System.Text.RegularExpressions
System.Threading
System.Threading.Thread
System.Xml.ReaderWriter
System.Xml.XmlSerializer

# How the stand-in for the server's own library is written. That interface has
# eighty-one members and this suite needs two of them, so the stand-in is a
# runtime proxy refusing everything it was not arranged for rather than eighty-
# one hand-written members that throw. It is the runtime the server already runs
# on rather than a mocking package, which is the argument
# ServerLibraryAdapterStandIn.cs makes at itself, and it is #89's.
System.Reflection.DispatchProxy
